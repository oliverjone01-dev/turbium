# pereezd - переезд в новую сессию

Цель: пользователь не следит за лимитами и не открывает окна руками. Длинная сессия дорогая
(каждый ход заново перечитывает весь контекст) и тупеет (важное тонет в шуме). Переезд
короткий и автоматический: пользователь видит одну строку «переезд» и ссылку на новую сессию.

## Когда

| Сигнал | Действие |
|---|---|
| Метка хука `[pereezd] ... ОБЯЗАТЕЛЕН` (контекст от 200K) | Переезд сразу. Текущий запрос пользователя уходит в новую сессию дословно |
| Метка хука о 150K и выше | Доделать текущий шаг, переехать на ближайшей точке сохранения |
| Метка хука «кэш остыл» | Переехать, если запрос начинает новую задачу |
| Закрыта крупная подзадача (PR смержен, модуль готов), дальше другая тема | Переехать |
| Пользователь сказал «переезд» или `/pereezd` | Переехать |
| Пользователь написал «без переезда» | Не переезжать в этом ходе |

Не переезжать посреди правки: сначала довести изменение до сохранённого состояния.

Хука нет (Cowork, чат без плагина)? Размер контекста: `get_session` без `session_id`,
поле `external_metadata.context_usage.used_tokens`. Инструмента нет - ориентироваться на
длину переписки: десятки больших ходов с файлами и выводами инструментов = пора.

## Файлы из чата (главное правило)

Пользователь не должен присылать один и тот же файл дважды. Поэтому файл сохраняется
**в том же ходе, когда пришёл**, а не при переезде: тогда обрезать сессию можно в любой момент.
Датчик context-meter сам напоминает о несохранённых вложениях и даёт полный путь к скрипту.

- **Где искать присланное:** `/mnt/user-data/uploads/`, `/mnt/attach/`, пути, которые назвал
  пользователь, скрэтчпад и `/tmp`. Быстро: `ls -la /mnt/user-data/uploads /mnt/attach 2>/dev/null`.
- **Сохранить:** `bash <папка этого скилла>/scripts/save-file.sh [--no-pii] <файл> "<что важного одной строкой>" [откуда]`.
  Копия ляжет в `sessions/files/<дата>-<имя>` (одинаковые имена не затирают друг друга),
  строка в реестр `sessions/files/INDEX.md` (где, откуда, размер, sha256, дата, суть),
  `git add` сделан. Дальше **коммит и пуш в этом же ходе**: контейнер одноразовый.
- **Приватное или больше 50 МБ:** в репозиторий не копировать. `--link <ссылка>`: в реестре
  ссылка на хранилище и sha256 оригинала, датчик считает файл сохранённым.
  Разовый файл, который дальше не нужен: `--link "не нужен дальше"`.
- **Публичный репозиторий или неясно:** задать `PEREEZD_PUBLIC_REPO=1` (env в настройках
  проекта); тогда без `--no-pii` скрипт не копирует. `--no-pii` ставить, только проверив, что
  в файле нет персональных данных, цен, договоров и токенов. Приватное - в приватное
  хранилище (диск через коннектор, приватный репозиторий) по `--link`, с учётом местного
  закона о персональных данных. Некуда - `--link "только в старой сессии <ссылка>"` и
  выжимка без чувствительного в `sessions/files/<имя>.md`. Токены и пароли не сохранять
  никогда, только имя переменной окружения.
- **Файла на диске нет** (картинка или текст вставлены прямо в сообщение): записать
  `sessions/files/<дата>-<имя>.md`. Текст до ~2K токенов - целиком, больше - структура и
  ключевые куски. Картинка - что на ней, все цифры и надписи дословно. Строку в реестр
  дописать руками с пометкой «выжимка, оригинал в старом чате <ссылка>». Датчик такие
  вложения не видит, тут всё на дисциплине.
- **Большие файлы** (xlsx, json, выгрузки): в контекст и в handoff не тащить. В колонку
  «что важного» - итог скрипта: строки, колонки, период, суммы.
- **Режим Папка:** то же в рабочей папке. **Режим Чат:** выжимку каждого файла в раздел
  «Файлы из чата» handoff. В обычном чате без файловой системы оригинал может понадобиться
  прислать ещё раз: об этом честно сказать в handoff.
**Новая сессия никогда не просит файл, который есть в реестре.** Перед любой просьбой
«пришли файл»: `grep -i <имя или тема> sessions/files/INDEX.md`, а если реестра нет на
текущей ветке - `git fetch origin && git log --all --oneline -- sessions/files/INDEX.md` и
`git show <ветка>:sessions/files/INDEX.md`. Просить можно только то, чего нигде нет, и один раз.

## Умная точка обрезки

- Переезд только когда все файлы этого и прошлых ходов в реестре. Файл пришёл в том же
  сообщении, что и сигнал 200K: сначала сохранить файл и закоммитить, потом переезд.
- Резать по последнему законченному шагу с коммитом. Незаконченный запрос уходит в новую
  сессию дословно вместе со списком файлов из реестра, к которым он относится.
- В handoff выводы, пути и итоги скриптов, а не содержимое: новая сессия откроет файл сама,
  если он понадобится.

## Режим работы

Определить один раз в начале переезда:

- **Режим Git** - есть git-репозиторий с remote (`git remote -v` не пустой). Обычно Claude Code
  в облаке, CLI, десктоп.
- **Режим Папка** - репозитория нет, но есть рабочая папка (Cowork, локальный проект без git).
- **Режим Чат** - нет ни репозитория, ни папки для записи.

## Порядок

### 1. Объявить
Одна строка: «Переезд: контекст NNNK, сохраняю и открываю <название>. Секунду.»
Разрешения не спрашивать.

### 2. Сохранить работу
- Git: `git status`, всё несохранённое закоммитить осмысленным сообщением и запушить
  в текущую рабочую ветку. Только не-main: если сессия стоит на main, сначала завести
  рабочую ветку.
- Критический артефакт (публикация, продукт, крупный бюджет) без вердикта проверяющего
  (отдельный агент-аудитор, если он есть в проекте): в коммите префикс `WIP:`, в передаточном файле пометка
  «аудит не пройден» с перечнем таких артефактов.
- Папка: убедиться, что результаты лежат файлами в рабочей папке, а не только в чате.
- Нужные дальше файлы из `/tmp` или временной папки перенести в проект, иначе назвать их
  в передаточном файле как «утеряно при переезде».

- Файлы из чата: сверить, что всё присланное за сессию есть в `sessions/files/INDEX.md`
  (правило выше). Чего нет - сохранить сейчас, до handoff.

### 3. Передаточный файл
Путь: `sessions/handoff/<ГГГГ-ММ-ДД>-<проект>-<задача>-v<N>.md` (латиница, дефисы).
Шаблон: `sessions/handoff/_TEMPLATE.md` проекта, а если его нет - `templates/handoff.md`
рядом с этим файлом (скопировать в `sessions/handoff/_TEMPLATE.md`, чтобы дальше жил в проекте).
Бюджет до ~4K токенов: выжимка, а не пересказ. Разделы шаблона обязательны все, включая «Файлы из чата» (ссылка на реестр и какие файлы нужны для следующего шага).

Решения, принятые с пользователем, записать в раздел «Решения». Если в проекте есть
`knowledge/decisions.md` и `knowledge/facts.md`, долгоживущие решения и проверенные цифры
с источником продублировать туда одной строкой.

Самопроверка: сможет ли сильный специалист, не видевший этот чат, продолжить по файлу без
единого вопроса? Если нет, дописать.

- Git: коммит и пуш.
- Папка: файл сохранён в рабочей папке.
- Чат: текст handoff целиком идёт в стартовый промпт новой сессии (шаг 5).

### 4. Фон старой сессии
Если доступны инструменты рутин и PR (`list_triggers`, `unsubscribe_pr_activity`):
- Включённые рутины с `persistent_session_id` этой сессии: разовые чек-ины удалить
  (`delete_trigger`). Нужна проверка - новая сессия поставит свою по правилам ниже.
- Открытые PR: `unsubscribe_pr_activity` здесь, подписку оформит новая сессия.

Инструментов нет - перечислить рутины и PR в разделе «Фон» handoff.

### 5. Новая сессия
Название `<Проект> - <Задача> - v<N+1>`, например «Сайт - Лендинг - v3».
Коротко, по-русски, без дат. Номер неизвестен - прошлая считается v1.

**Есть `create_session`** (Claude Code в облаке, облачный Cowork):
- `get_session` без аргументов: repo URL из `session_context.sources`, ветка из `outcomes`
  или `external_metadata.current_branches`, модель из `session_context.model`.
- `create_session`: `title`; в режиме Git `source_url` = repo URL, `source_revision` и
  `outcome_branch` = текущая ветка; `model` = та же, что сейчас (модель не понижать:
  экономия идёт на длине контекста, а не на качестве мышления); `prompt` = стартовый
  промпт ниже; `permission_mode` не передавать.

**`create_session` нет** (локальный Cowork, CLI без облака): вывести пользователю стартовый
промпт одним блоком и одну строку «Открой новую сессию (новый чат / `claude` в той же папке)
и вставь это». Больше ничего не делать.

Стартовый промпт:

```
Ты продолжаешь цепочку «<Название>» (v<N+1>). Прошлая сессия: <ссылка или «локальная»>.
1. Прочитай CLAUDE.md (если есть) и sessions/handoff/<файл>.md целиком. Историю переписки не ищи, всё нужное в файле.
2. Раздел «Решения» не пересматривай, сделанное не переделывай.
3. Одной строкой подтверди пользователю: что за цепочка и какой следующий шаг.
4. Выполни «Следующий шаг».<если был незакрытый запрос:> Затем запрос пользователя дословно: «...»
5. Файлы, присланные раньше, лежат в sessions/files/ (реестр INDEX.md): бери оттуда, пользователя повторно не проси.
6. Открытые PR из раздела «Фон»: subscribe_pr_activity. Чек-ины только по правилам скилла pereezd.
<Git:> Работай на ветке <ветка>.
```

В режиме Чат вместо пункта 1 вставить текст handoff целиком.

### 6. Отчёт
- Если сессия создана инструментом: `get_session(<новый id>)` подтверждает создание;
  старую переименовать (`set_session_title`): `<старое название> -> перенесено в v<N+1>`.
  Не архивировать: пользователь может захотеть заглянуть назад.
- Пользователю: «Готово. Продолжаем в <название>: <ссылка>». В старой сессии больше ничего
  не делать.

## Правила чек-инов
- GitHub сам будит сессию на CI, ревью и мерж. Чек-ин только страховка.
- Первый через ~50 минут, дальше раз в 4 часа. Ночью по времени пользователя (по умолчанию
  23:00-08:00 МСК) не ставить.
- После 3 пустых проверок подряд остановиться.
- Никогда не ставить шаг около 60 минут: кэш живёт час, каждое пробуждение станет полным
  промахом и перепишет весь контекст по полной цене.
- Опрос чатов и страниц каждые несколько минут запрещён: нужен webhook (`watch_url`, n8n).
- Длинная слежка (PR, деплой) живёт в отдельной маленькой сессии на лёгкой модели,
  а не в рабочей.

## Чего не делать
- Не просить у пользователя файл, который есть в реестре `sessions/files/INDEX.md`.
- Не переезжать, пока присланные файлы не сохранены.
- Не спрашивать разрешения на переезд.
- Не понижать модель и не выключать режим мышления.
- Не класть в handoff сырые логи, дампы и выводы инструментов. Только выводы и ссылки.
- Не переезжать, если несохранённое не сохраняется (пуш падает, папка недоступна).
  Сказать, в чём проблема.
